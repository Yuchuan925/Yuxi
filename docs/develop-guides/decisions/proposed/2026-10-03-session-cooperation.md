# 统一 Session 协作模型

状态：proposed
类型：architecture
Owner：backend/yuxi/modules/agents/services/subagents.py

## 问题

协作需要多个拥有独立上下文的会话共同完成工作。现有 SubAgent 专用身份、后端、配置目录和调用限制，使同一套会话执行能力出现两套使用方式。目标是统一会话的创建、输入、执行和观察，以会话之间的委派关系表达协作。

本文供维护者审阅概念、接口和生命周期取舍；前置知识见 [架构说明](https://github.com/xerrors/Yuxi/blob/main/ARCHITECTURE.md)。本文中的接口与行为均为拟议方案，不能作为已实现能力引用。原[调研](../../audits/subagent-cooperation-research-2026-10-03.md)仅作背景，方案以本文为审阅对象。

## 提案

### 概念与身份

| 概念 | 职责 |
| --- | --- |
| Agent | 可复用的模型、指令与能力配置 |
| Session | 独立上下文及输入队列的会话实例；内部继续复用 Thread |
| Input / Turn / Run | 持久接收的输入 / 一轮工作 / 一轮中的执行段，沿用现有归属与结果规则 |
| 协作树 | Session 的创建关系；树内成员可互发消息、追加输入、取消指定 Turn |

移除 `is_subagent`、`SubAgentBackend`、子智能体专用目录和白名单配置入口。新会话使用派发方的 Agent 配置，默认继承其实际模型、能力配置与授权约束；不提供另选专业 Agent 配置的协作入口。角色与交付要求写入任务描述。新会话只接收显式描述，不复制父历史、checkpoint 或附件上下文，不提供 fork；共享目录中的文件仍可按权限读取。

使用稳定 `session_id` 做持久身份、路由和授权校验；委派关系保存父 Session、局部唯一名称及创建来源 Run。名称路径如 `/root/reviewer` 在当前树内解析到 ID，不能单凭路径授权。名称创建后固定、显示标题可修改，第一版不支持改挂父节点。创建关系为树，通信与控制允许跨兄弟节点及层级，包括向根 Session 提交输入。

### 协作接口

借鉴 [OpenAI Responses multi-agent](https://developers.openai.com/api/docs/guides/responses-multi-agent) 的协作方式，工具名称与 Yuxi 概念对齐，不新增 Task 实体或复用 Durable Task 状态。

| 工具 | 行为与返回边界 |
| --- | --- |
| `create_session` | 创建关联会话并提交首个 Input，立即返回会话身份、名称路径与输入回执；有 Turn 时返回其 ID |
| `send_message` | 向树内会话投递协作消息；运行中在安全边界读取，空闲时留待下次执行，不创建 Turn 或自动唤醒 |
| `submit_input` | 向树内会话提交新工作；空闲时调度，忙碌时按 FIFO 排队，等待用户回答或审批时明确拒绝 |
| `cancel_turn` | 按 Session ID 与 Turn ID 取消指定工作；保留历史与既有副作用，不暂停、不承诺断点恢复 |
| `wait_sessions` | 等待指定会话的消息或工作状态更新，任一有更新即返回；携带消费位置与明确超时结果 |
| `list_sessions` | 返回当前协作树及成员状态，区分会话存在、当前 Turn 状态和输入排队状态 |

用户可直接打开子 Session，使用相同输入、steer、回答与审批入口。新工作由 `submit_input` 发起；运行中方向修正沿用现有 steer 语义。完成、失败、取消和等待用户均形成可观察更新，绑定来源 Session 与对应 Turn/Run。父 Turn 正常结束或失败不终止子 Turn；完成通知持久保存，默认不唤醒已结束的父任务。普通 `cancel_turn` 只影响指定 Turn；用户显式“停止全部”才沿协作树取消在途工作并停止消费待处理队列。队列沿用现有显式继续入口重新调度；继续队列不恢复已取消的 Turn，不引入任务暂停/恢复工具。

### 调度、消息与共享环境

允许递归创建会话；根与所有后代共用 4 个执行名额，按整树原子领取，不能按每父节点分别计数。排队、等待协作更新和等待用户不占执行名额；恢复可执行状态时重新领取。协作等待需持久记录唤醒条件、消费位置和超时，并释放实际 worker 执行槽，避免仅释放逻辑名额却让子会话无法执行。这是内部调度等待，不提供用户可操作的暂停/恢复功能。

PostgreSQL 拥有消息、回执、等待条件和终态事实；事务提交后才发布 Redis/ARQ 通知。创建、提交和消息投递使用幂等键，重试不重复创建会话或输入。消息保留发送者、接收者、来源执行与处理位置，区分已接收和已处理；协作文本不提升为用户授权。结果按目标 Turn 的 `result_run_id` 读取，不取会话的“最新输出”猜测结果。执行失败有明确终态，唤醒失败可从持久事实补投。

同树默认共享派发方的实际沙盒与 Project Workdir，包括已安装软件、后台进程和端口；各 Session 独立拥有上下文、checkpoint 和 Run lease。任务终态发布与共享沙盒清理解耦，某个 Run 结束或取消不能销毁其他成员使用的环境。取消操作只停止目标执行拥有的活动，不以销毁整个沙盒替代取消；已经分离的共享后台服务不承诺随单个 Turn 取消而回滚。

共享沙盒空闲一段时间后释放，工作目录保留；下一次执行可重建环境，但不承诺恢复后台进程和临时环境。空闲判定与新执行领取须串行协调，活动工具不能被误回收。具体超时值属于实施时需要明确的运行参数，本文不增加配置体系。共享文件的并行写入由任务分工协调，第一版不引入自动合并、文件锁平台或 worktree 隔离。

树成员必须处于相同用户、APP 与授权作用域，委派不扩大权限。工具执行、审批和知识库可见性走统一后端边界；共享沙盒不承担不同信任身份之间的隔离。用户直接干预成员会话时，向父 Session 投递变更通知，通知本身不自动启动工作。

### 实现方案

| 语义 Owner | 改造职责 |
| --- | --- |
| agents 的 models / repositories / migrations | 统一会话身份，持久化委派关系、协作消息及等待事实，保证树内命名、幂等与作用域约束 |
| agents 的 services / scheduler / runner | 复用 Input → Turn → Run 主链路；实现树级并发、等待释放与唤醒、精确取消和终态通知 |
| agents 的 runtime / middlewares | 用统一后端装配六个协作工具，去除专用 SubAgent 后端与身份型能力限制 |
| runtime/sandbox 与 workspace | 分离共享沙盒归属和 Session 执行归属，协调空闲释放与重新使用，保留持久目录边界 |
| API 与前端 conversation / agents | 复用会话输入和观察入口，展示协作树、成员产物与审批，移除专用子智能体配置入口 |

主链路为：工具或用户输入 → 授权后的会话服务 → 持久回执与队列 → 提交后调度 → 领取树级名额执行 → 持久输出和通知。恢复与事件重放读取各自事实 Owner，前端只投影已授权状态。树级观察可聚合更新，完整消息和产物始终归属于产生它们的 Session/Turn/Run。

实施须核对已有 Agent 配置、历史子会话、Run 类型约束、公开 API/事件及前端消费者，显式制定数据迁移与兼容处理；保留历史结果和归属，不能直接删列或把旧配置静默重置。当前审批等待和 steer 所需的 Run 接续继续保留。

## 替代方案

- 保留特殊 SubAgent 并补工具：仍需维护两套配置与能力规则，不满足统一会话的目标。
- 仅统一后端、保留子智能体目录：能减少代码重复，但用户和模型仍需理解特殊身份与白名单。
- 统一 Session 并以委派关系协作：采用；复用执行底座，新增必要的消息与调度语义。
- 直接托管到 Responses API：不采用为本方案前提；Yuxi 继续拥有多模型接入、持久状态与共享沙盒。

非目标：上下文继承或 fork、用户暂停/断点恢复、跨树协作、改挂父节点、新 Task 状态机、自动写冲突解决，以及全局 Thread 重命名。

## 验收标准

以下均为实施验收计划，当前结果为 `Not run`，原因是本次仅形成方案文档。直接证据按[测试规范](../../testing-guidelines.md)在真实 PostgreSQL、HTTP、worker 与浏览器边界执行；独立 Reviewer 检查未闭合语义，不以文档构建代替产品证据。

| 验收主张 | 失败面 | 语义 Owner | 直接证据 / 命令 | 负向案例 | 当前结果 |
| --- | --- | --- | --- | --- | --- |
| 统一会话、独立上下文、递归可用 | 仍走特殊后端或复制父历史 | runtime、会话服务 | E2E：根→子→孙，读取配置和各自消息 | 禁止孙代、注入父历史即失败 | Not run |
| 整树最多 4 个执行，等待可推进 | 并发超额或 worker 饥饿 | scheduler、runner | 真实 PG 并发与满槽 E2E，读取 lease/执行区间 | 每父计数或等待占满 worker 时失败 | Not run |
| 投递幂等、消息不自动唤醒、结果不串轮 | 重复派发、错读新一轮结果 | 消息/输入 repositories、通知服务 | HTTP 与崩溃恢复测试，回读消息、回执和目标 Turn | 重投重复创建、通知启动新 Turn 即失败 | Not run |
| 树内控制与用户直接交互一致 | 越权、取消错 Turn、审批被绕过 | 会话服务、授权查询、前端 | HTTP/E2E：兄弟互发、直接输入、审批与取消竞态 | 跨树/APP、旧 Turn 取消新 Turn 均拒绝 | Not run |
| 沙盒共享且安全释放 | 父结束误销毁子环境、空闲回收竞态 | sandbox、leases、workspace | E2E：共用文件/端口、取消单 Turn、空闲重建 | 活跃使用者存在时销毁沙盒即失败 | Not run |
| 旧表面移除且历史可读 | 残留入口或迁移丢失结果 | migration、API、前端 | 迁移 fixture、接口/DOM 回读及生产源码负向搜索 | 旧后端仍注册、历史归属失效即失败 | Not run |

旧能力不存在：实施后生产装配、配置 schema 与管理入口不再包含 `is_subagent`、`SubAgentBackend` 和专用子智能体白名单；迁移与历史记录中保留必要旧标识。重新引入条件：存在统一会话配置与授权无法表达的真实产品需求，并另立决策论证。

## 风险

- 共享沙盒允许成员互相影响文件、进程和端口；这是已接受的协作边界，不能作为互不信任执行的隔离方案。
- 树内任意成员可追加输入或取消工作，可能发生相互取消或持续派工；操作记录发起者、明确目标，并可由用户停止整树。4 个并发名额只限制同时执行，不限制累计成本。
- 等待唤醒、并发领取、取消与沙盒回收跨事务和 worker，必须验证崩溃与竞态。内部等待持久化不得演变成另一套公开暂停状态机。
- 旧数据、事件消费者和审批恢复路径都有当前消费者；具体迁移步骤、消息消费与 checkpoint 的一致性方案、沙盒空闲超时需在实施设计中闭合，不能以删除旧代码代替。
